# Правила разработки Pawinder

## 1. Ветки

- Основная ветка проекта — `master`.
- Прямые изменения в `master` запрещены.
- Новые функции, исправления и документация разрабатываются в отдельных ветках - ветки kazakova и ponomaryova. Ветки с -patch создаются для изменений не связанных с основным кодом, а затем удаляются.
- Изменения попадают в `main` только через Pull Request (PR).

## 2. Требования к PR

Каждый PR должен содержать:
1. Краткое описание изменений.
2. Ссылку на Issue, если задача закрыта.

PR не должен включать несвязанные изменения, временные файлы, секреты или сгенерированные файлы сборки.

## 3. Автоматические проверки

Для автоматической проверки изменений используется GitHub Actions.

Workflow запускается при открытии Pull Request и обновлении его содержимого. На текущем этапе автоматические проверки используются для контроля успешной сборки проекта.

Автоматические тесты планируется добавить по мере реализации функциональности. После их добавления они должны запускаться в рамках GitHub Actions.

Перед слиянием PR должны успешно проходить все проверки, настроенные в качестве обязательных в правилах защиты ветки main.

## 4. Независимое review

- Значимые изменения проверяет участник команды, который не является автором PR.
- Проверяющий оценивает логику, соответствие требованиям, обработку ошибок и безопасность.
- Одобрение должно быть получено до слияния.
- После существенных новых изменений PR повторно проверяется.
- Настройки защиты ветки изменяет участник с соответствующими правами.

## 5. Защита основной ветки

- запрет прямого push;
- обязательный PR;
- обязательные статусные проверки;
- обязательное одобрение другим участником.

Если используется CODEOWNERS, необходимо отдельно настроить обязательное одобрение владельца кода. Файл CODEOWNERS сам по себе не включает защиту ветки.

## 6. Definition of Done (DoD)

Изменение считается готовым к слиянию, если выполнены применимые пункты чек-листа:

- [ ] Понятно, какую задачу или требование решает изменение.
- [ ] Выполнены применимые проверки, их результаты доступны.
- [ ] Для изменения поведения указан способ проверки результата.
- [ ] Обновлена затронутая документация, инструкция, конфигурация или требование.
- [ ] В код, логи и диагностические сообщения не добавлены пароли, токены и другие секретные данные.
- [ ] Для значимого изменения проведено независимое review.
- [ ] Существенные замечания проверяющего устранены или согласованно разрешены.

Если автоматические тесты для изменяемой функциональности ещё не реализованы, необходимо выполнить доступные проверки и указать это в Pull Request. После появления тестов их следует включать в соответствующие проверки GitHub Actions.

## 7. Значимые изменения

К значимым изменениям Pawinder относятся:

- изменение архитектуры Android-клиента или Spring Boot backend;
- изменение API-контрактов и формата передаваемых данных;
- изменение существенных требований к приложению;
- изменение структуры базы данных;
- изменение конфигурации сборки Android или backend;
- изменение процесса сборки и поставки приложения;
- исправление критических дефектов;
- добавление мер защиты, например проверки доступа к пользовательским данным.

Такие изменения требуют независимого review участником команды, который не является автором Pull Request. До слияния необходимо проверить корректность решения, обработку ошибок, безопасность и соответствие требованиям.

## 8. Пример содержательного замечания при review

**Задача:** реализовать сохранение понравившихся животных в избранном.

**Замечание проверяющего:**

> Не определено поведение при повторном добавлении одного и того же животного в избранное. В результате один питомец может отображаться в списке несколько раз. Нужно уточнить ожидаемое поведение и добавить проверку повторного добавления.

**Ожидаемое решение:**

1. Уточнить требование: одно животное не должно дублироваться в избранном одного пользователя.
2. Реализовать проверку повторного добавления.
3. Добавить автоматический тест после реализации тестовой инфраструктуры.
4. Повторно проверить изменение и устранить замечание до слияния PR.

Качество review определяется тем, насколько замечания выявляют реальные проблемы и помогают их устранить, а не количеством комментариев или одобрений.

## 9. Применение DoD в Pawinder

При реализации новой функции, например обработки свайпов, разработчик создаёт Issue с критериями приёмки, выполняет изменения в отдельной ветке, запускает сборку и доступные проверки, а затем открывает Pull Request.

GitHub Actions выполняет настроенные автоматические проверки. Второй участник команды проверяет значимые изменения, оставляет замечания при необходимости и подтверждает готовность после их устранения.

Слияние в `main` выполняется после выполнения обязательных условий, установленных в правилах репозитория.
