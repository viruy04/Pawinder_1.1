# Правила разработки Pawinder

## 1. Ветки

- Основная ветка проекта — `main`.
- Прямые изменения в `main` запрещены.
- Новые функции, исправления и документация разрабатываются в отдельных ветках - ветки kazakova и ponomaryova. Ветки с -patch создаются для изменений не связанных с основным кодом, а затем удаляются.
- Изменения попадают в `main` только через Pull Request (PR).

## 2. Требования к PR

Каждый PR должен содержать:
1. Краткое описание изменений.
2. Ссылку на Issue, если задача закрыта.

PR не должен включать несвязанные изменения, временные файлы, секреты или сгенерированные файлы сборки.

## 3. Автоматические проверки

Для автоматической проверки изменений используется GitHub Actions.

Workflow запускается при открытии Pull Request и обновлении его содержимого. На текущем этапе автоматические проверки используются для контроля успешной сборки проекта.

Автоматические тесты планируется добавить по мере реализации функциональности. После их добавления они должны запускаться в рамках GitHub Actions.

Перед слиянием PR должны успешно проходить все проверки, настроенные в качестве обязательных в правилах защиты ветки main.

## 4. Независимое review

- Значимые изменения проверяет участник команды, который не является автором PR.
- Проверяющий оценивает логику, соответствие требованиям, обработку ошибок и безопасность.
- Одобрение должно быть получено до слияния.
- После существенных новых изменений PR повторно проверяется.
- Настройки защиты ветки изменяет участник с соответствующими правами.

## 5. Защита основной ветки

- запрет прямого push;
- обязательный PR;
- обязательные статусные проверки;
- обязательное одобрение другим участником.

Если используется CODEOWNERS, необходимо отдельно настроить обязательное одобрение владельца кода. Файл CODEOWNERS сам по себе не включает защиту ветки.

## 6. Definition of Done (DoD)

Задача считается завершённой, когда:
- [ ] Реализация соответствует описанию Issue.
- [ ] Критерии приёмки выполнены.
- [ ] Проект собирается без ошибок.
- [ ] Соответствующие автоматические тесты пройдены.
- [ ] Ошибки и граничные случаи обработаны.
- [ ] Документация обновлена при необходимости.
- [ ] PR проверен независимым участником.
- [ ] Обязательные проверки GitHub Actions прошли.
- [ ] PR принят и слит в `main` согласно правилам репозитория.

## 7. Пример применения правил

**Задача:** реализовать модуль распознавания свайпов.

1. Создать GitHub Issue с критериями: распознавать левый и правый свайпы, игнорировать долгие зажатия.
2. Добавить модуль.
3. Выполнить сборку.
4. Создать PR, указать Issue и результаты проверок.
5. Дождаться GitHub Actions.
6. Получить независимое review и исправить замечания.
7. Слить PR после выполнения обязательных условий.

**Ожидаемый результат:** изменение попадает в `main` только после проверки кода, успешного прохождения обязательных проверок и независимого одобрения.
